# ARM64 JIT on Android

The reusable leaf JIT in [vm/jit-arm64.flex](../vm/jit-arm64.flex) generates ARM64
instructions from the VM's word IR at runtime. The Android demo executes this
generated code inside its process. No executable file, APK installation or
external compiler is involved in an individual JIT compilation.

The generator is written in Flexscript. Its stateless instruction encoders in
[lib/arm64-code.flex](../lib/arm64-code.flex) are shared with the existing ARM64
compiler backend. The small C host adapter handles executable memory, cache
synchronization and native calls.

## Execution model

1. Supply a verified leaf function's word IR and a trusted VM context.
2. Generate native instructions into a caller-owned writable buffer.
3. Copy the generated bytes to an anonymous read/write mapping.
4. Use `mprotect` to change that mapping to read/execute, then synchronize ARM64
   data and instruction caches with the required barriers.
5. Call the generated entry as `long entry(long *context)`.
6. Reuse the published code when the function's bytecode is unchanged.

The Android demo host has a bounded **one-entry cache**. It compares the complete
IR contents before reuse, so changing an immediate or branch invalidates the
cache. Code is immutable after publication; the host releases the old mapping
before publishing replacement code. Mappings are rounded to multiples of 64 KiB,
supporting kernels with 4-, 16- or 64-KiB pages without assuming a 4-KiB page.

## Supported instructions

The first version supports constants, locals, expression temporaries, signed
64-bit wrapping arithmetic, comparisons, masked shifts, unary operations,
conditional/unconditional branches, loops, returns, guest globals and checked
guest arrays. Division by zero and MIN/-1 return VM error 2, rather than causing
a native process trap. Invalid guest memory accesses return VM error 3.

Calls, allocation, arbitrary pointer builtins, raw guest syscalls, FFI and I/O
are not compiled. The generator returns a fallback result so a VM dispatcher can
keep those functions in its checked interpreter. Generated code performs only
the fixed host clock syscall used for deadline enforcement.

Every executed IR instruction consumes one unit of fuel, including a failing
arithmetic or bounds instruction. Exhaustion returns error 1 before the next
instruction. Backward branch sites count executions and check a configured
monotonic deadline every 1024 visits; expiration or clock failure returns error
8. A zero deadline disables the time check, while fuel checks remain active.

The optimized generator keeps fuel in x21 and the first seven local/temporary
slots in x22–x28. Further slots use short frame-relative loads/stores where
possible. All error guards branch to shared exits. The entry saves/restores
x19–x28 and publishes exact remaining fuel on every exit.

For multi-instruction basic blocks, a budget check selects a fast copy when fuel
covers the entire block. That copy prepays the block's fuel, removing per-IR fuel
checks. Arithmetic/bounds errors refund the unexecuted suffix before returning.
With insufficient fuel, a checked copy executes the prefix one instruction at a
time, retaining guest writes before exhaustion. Checked copies sit after the
hot blocks. Branch targets and fallthroughs start new blocks; one-instruction
blocks use only the checked copy. No additional scratch is needed.

Fast blocks use local registers directly, remove adjacent expression copies,
write arithmetic results directly into following local-store destinations, and
lower suitable constants to immediate or shifted-add instructions. Comparisons
can supply a following conditional branch's flags directly. Simple while loops
rotate their header into the body: a single budget check prepays the body and
its next header, followed by a direct conditional branch back to the body.
Failure refunds include any unexecuted prepaid header. The checked copies
retain the original control flow.

Heap base/size, the first array base, backedge count and deadline remain in registers. The first guest
declaration's extent/base validity is computed once and tested at each access;
other declarations retain their own extent checks. A successful array load can
validate a later store using the same saved expression-stack index and identical
declaration. Popping or replacing that slot invalidates the proof. Every guest
access remains validated, and deadline/fuel accounting retains the VM semantics.
Fast code also tracks unsigned upper bounds from constants, boolean results and
AND masks. A load index whose bound fits its declared span needs no dynamic
index check. Comparison results are left in CPU flags when both branch arms
immediately overwrite the accumulator; live boolean results are still emitted.

Eligible rotated loops of at most 64 IR records also have four-iteration copies.
A group starts only when fuel covers all four traces and the first declaration's
cached heap validity is true (if the function uses guest memory). Rejected groups
enter the ordinary trace without changing guest state. Every iteration still
evaluates the original loop condition and increments its original backedge
counter; early exits and failures refund all unexecuted headers/iterations.

A runtime deadline check selects one of two groups. With a zero deadline, the
copies omit clock work. With a deadline, they retain the clock syscall at every
1024th VM backedge and exact deadline failure/refund behavior. Insufficient-fuel
tails use the ordinary trace and checked copies. These variants trade code size
and compilation work for faster repeated execution; ordinary large loops are
not unrolled. Scratch and context sizes remain unchanged.

## Generator API and context

```flex
arm64_jit_compile(ir, bytes, code, capacity, scratch, scratch_bytes)
```

The input contains one function starting with `(18, slots)`. Each instruction
is two 64-bit words. Branch operands are byte offsets within this input buffer.
A VM dispatcher extracting a function from a larger IR image must rebase its
branch operands to that function's start. Function size is limited to 8192 IR
records and locals to 4096 slots.

`code` and `scratch` are separate caller-owned buffers, also separate from the
IR. Code capacity may be up to 1 MiB. Scratch requires at least `bytes * 3 / 2`
bytes. The caller publishes code only when the result is positive:

| Result | Meaning |
|---|---|
| Positive | Generated code size in bytes |
| -1 | Unsupported instruction; use the interpreter |
| -2 | Malformed IR, invalid slots, targets, or expression stack |
| -3 | Output or scratch capacity is insufficient |

Native entry x0 points to nine trusted 64-bit context words:

| Index | Meaning |
|---|---|
| 0 | Native pointer to the initial local slots |
| 1 | Remaining fuel, updated by generated code |
| 2 | VM error, initialized to zero by the caller |
| 3 | Backward-branch counter |
| 4 | Monotonic deadline in nanoseconds, or zero |
| 5–6 | Scratch timespec for the deadline check |
| 7 | Native guest-heap base |
| 8 | Guest-heap capacity in bytes |

Guest global and array operands are offsets, not host pointers. The host owns
this context and supplies appropriate memory extents and execution budgets.
The context, initial locals and generator buffers must not overlap guest memory.
Native local/temporary storage lives in registers and the generated function's
stack frame. The entry preserves AAPCS64 callee-saved registers x19–x29.

The generator uses module globals and is not reentrant. Hosts must serialize
compilation and cache publication. The demo's JNI methods synchronize on their
Java class; its test suite runs on a worker thread to keep the UI responsive.

This is a reusable ARM64 leaf JIT and an Android embedding. The existing
[x86-64 VM dispatcher](../vm/jit.flex) remains unchanged. Automatic hot-function
selection in an ARM64-hosted `flexscript run`, the full compiler/runtime port,
and a multi-function code cache are subsequent integration work. The x86 JIT's
64-byte context is not interchangeable with this JIT's 72-byte context.

## Verification

```sh
python3 scripts/test-arm64-jit.py --compiler build/flex-android
python3 scripts/build-android.py --compiler build/flex-android \
  --java-home /home/teppo/.gradle/jdks/eclipse_adoptium-17-amd64-linux.2
python3 scripts/test-android.py --compiler build/flex-android \
  --serial emulator-5580 --out build/android/jit-test
```

Use the SDK/JDK paths appropriate for your machine. Start the emulator with
`-no-window` as described in [the Android backend guide](android.md).

The fixture generator includes an independent Python word-IR interpreter.
4,842 cases compare full 64-bit results, exact remaining fuel, VM errors,
backedge counts and guest-heap hashes. They cover arithmetic boundaries, loops, cache reuse and
invalidation, large frames, division errors, guest bounds, deadline/fuel limits,
malformed IR and unsupported operations. Additional QEMU checks sweep every
output-byte capacity through a complete generated function, verify canaries and
scratch capacity, and retry compilation after partial failures. A guard page
after the output catches reads as well as writes beyond a failed emission.
An assembly caller also verifies x19–x29 preservation on fast and checked success/error exits.
Additional cases cover full-width immediates, aliased arithmetic destinations,
rotated-loop fuel/refunds, array-check invalidation, and live/expired deadlines
across repeated checked array updates. Unrolled cases exercise every early-exit
phase, signed induction boundaries, live boolean exits, partial-fuel tails,
range-proof invalidation, and heap/division failures in each group phase.
Direct context tests check clock syscall register preservation and backward conditional sites that do not take a branch.
Direct contexts force clock expiration in each of the four unrolled bodies.

The same fixture bytes are embedded in the demo APK. The Android test runner
reads back every native result record and checks it independently. It also
checks memory permissions, repeated event cache hits, rendering, touch input,
background/resume, cold restart and fatal logs. Results and screenshots are
saved in the test output directory.

Initial verification passed under QEMU Linux user emulation and a headless
Android 16/API 36 x86-64 emulator using `libndk_translation.so` for ARM64. That
translation layer reports the guest code's host mapping as `r--p`, despite the
successful RX protection request and execution; translated instructions are
managed separately by the native bridge. Tests require a non-writable mapping
there, and require `r-xp` on native ARM64 Android. Physical ARM64 instruction-cache
coherency and phone execution have not yet been verified.

References: [ARM64 cache synchronization](https://github.com/llvm/llvm-project/blob/main/compiler-rt/lib/builtins/clear_cache.c),
[Android ART JIT memory](https://android.googlesource.com/platform/art/+/master/runtime/jit/jit_memory_region.cc).

## Performance measurement

```sh
python3 scripts/bench-arm64-jit.py --compiler build/flex-android
# To compare with a preserved earlier generator:
python3 scripts/bench-arm64-jit.py --compiler build/flex-android \
  --generator /path/to/original/vm/jit-arm64.flex --out build/jit-baseline-bench
python3 scripts/bench-arm64-jit.py --compiler build/flex-android \
  --baseline-report build/jit-baseline-bench/report.json
# Use the same allowed CPU for both runs when comparing under host load:
# append --cpu <number> to each command.
# Add --deadline to both runs to include periodic clock syscalls.
```

The benchmark uses integer hashing and checked array updates, comparing the
generated code with an independent C IR interpreter and separate Clang `-O2` C
kernels. The C workload selector runs outside the loops; neither C kernel pays
for a per-iteration selector branch.
It validates results, guest heap, fuel and backedge counts before timing. Each
reported call runs 20,000 loop iterations; timings are medians of nine samples
of 32 calls with rotating engine order. Compilation, executable publication,
IR-cache lookup and input resets are excluded. Compilation time is a separate
single cold observation, including QEMU translation warmup.
Raw generated bytes and disassembly are saved as `kernel-*.bin` and
`kernel-*.asm`. Reports include CPU affinity, the benchmark source hash and a
speedup normalized to each run's C measurement; paired comparisons should use
the same affinity, deadline mode and harness. The interpreter validates future
deadline runs without issuing clock syscalls; the JIT enforces those deadlines.

The first before/after QEMU run measured about 7.1x speedup for hashing and 5.4x
for checked arrays over the original JIT, and 23.9x/15.6x over the interpreter.
Generated sizes decreased from 1,688/2,560 to 968/1,488 bytes. The optimized JIT
still took about 4.0x/5.8x the corresponding C kernel time. These are emulated
warm-call measurements, not physical Android performance or full agent speed.

A previous optimization pass reduced the gap to C further. A paired run pinned
to the same CPU compared the block-metered JIT before and after that pass:

| Kernel | Before that pass | After that pass | Clang C | Speedup | After / C |
|---|---:|---:|---:|---:|---:|
| Integer hash | 291.4 us | 166.7 us | 89.2 us | 1.75x | 1.87x |
| Checked array update | 691.2 us | 285.9 us | 142.5 us | 2.42x | 2.01x |

Generated sizes decreased from 968/1,488 to 856/1,204 bytes. The C kernels have
no VM fuel, bounds or deadline policy. The remaining overhead includes these
checks; matching a C kernel is not a guarantee of matching full application
performance. These measurements still use QEMU, not a physical ARM64 phone.

The guarded-unrolling pass uses a stronger C baseline with separate kernels, so
its timings should be compared with its fresh paired baseline, not earlier
absolute times. Both generators run the same harness on CPU 8 under QEMU:

| Deadline | Kernel | Previous JIT | Current JIT | Clang C | Speedup | Current / C |
|---|---|---:|---:|---:|---:|---:|
| Disabled | Integer hash | 88.84 us | 53.46 us | 40.92 us | 1.66x | 1.31x |
| Disabled | Checked arrays | 166.76 us | 75.87 us | 59.83 us | 2.20x | 1.27x |
| Enabled | Integer hash | 116.79 us | 80.99 us | 41.03 us | 1.44x | 1.97x |
| Enabled | Checked arrays | 197.11 us | 111.19 us | 60.03 us | 1.77x | 1.85x |

Generated code grew from 856/1,204 to 1,552/2,044 bytes to hold the guarded
variants. The optimization applies to eligible instruction/loop patterns in
any supported ARM64 leaf function. The ahead-of-time compiler and x86 JIT are
unchanged. These warm-call QEMU results do not establish physical-phone speed.
