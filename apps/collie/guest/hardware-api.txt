
Hardware access discovery: hardware_access_info() reads the actual app SDK/target SDK, process UID, system_app/updated_system_app/debuggable package flags and17 fixed OS permission records {name,defined,requested,granted,protection_level}. defined=false means PackageManager has no permission definition and protection_level is typed null; protection_level is the raw SDK bitmask. These are observations, not proof of any hardware operation. A debuggable/system app, UID or granted privileged permission does not enable an absent adapter, prove root/vendor access, or bypass SELinux/Android policy. No runtime dialog, shell, device-node access, permission request or settings change is performed.
 hardware_restrictions() returns {platform,restrictions}; platform is a fresh hardware_access_info snapshot, restrictions are16 Flexscript descriptions for raw Wi-Fi/cellular/Bluetooth, USB gadget, internal I2C/SPI/GPIO, clocks, charging, global routing, raw input/device nodes and vendor services. These same rows are appended by hardware_capabilities(). Restricted rows deliberately report implemented=false, supported=null (device/vendor support unknown), available=false, discovery_implemented=true and code=adapter_unimplemented. requires/reason/alternative explain the missing integration and narrower public functions. An alternative has its own permissions and is not equivalent raw access; hid_open is Bluetooth HID, not USB gadget. A grant in platform.permissions never upgrades an unimplemented row. Reading discovery requires no hardware grant and never changes existing Ask/Allow/Deny choices. No vendor bridge is configured; hardware availability is unverified.

Sensor inventory returns a map with sensors/next/total; sensor_list_page uses offset and limit 1..32. next=-1 ends paging. Sensor/location measurements are db_real values with exact IEEE-754 bits in db_word. Subscriptions return handles for device_wait/device_close.
Sensor batching: sensor_batch_open(id,period_us,max_report_latency_us) uses the public SDK listener with requested period5000..1000000us and latency0..60000000us. sensor_open(id,period_us) remains the zero-latency form; one-shot sensors use trigger registration and reject positive batching latency. sensor_configure(handle,period_us,max_report_latency_us) explicitly unregisters/replaces the Android listener under the same owned continuous/on-change handle; valid reconfiguration has a delivery gap and a refused SDK registration closes the handle. Initial configuration is1 and increments on replacement; device_info and sample/accuracy/additional/flush events carry configuration so already queued earlier events remain distinguishable. Late callbacks from a replaced listener are ignored; one-shot trigger handles cannot be reconfigured or flushed. Period/latency are SDK hints, not measured delivery cadence or proof of physical batching/power savings; a device without a FIFO may deliver immediately. Inventory/info includes actual fifo_max_events/fifo_reserved_events, additional_info_supported, direct_report_max_rate and direct_memory_file_supported/direct_hardware_buffer_supported. Direct-report metadata describes advertised support; sensor_direct_open/configure below use the actual public shared-memory API. Subscription device_info retains sensor metadata and adds kind, period_us, max_report_latency_us, flush_pending and last_flush_completed; the latter two are typed null until present.
sensor_flush(handle,timeout_ms1..8000) submits one asynchronous public SDK flush and returns its positive per-listener request number. device_wait delivers flush_complete with sensor ID and matching request after the SDK callback; return from sensor_flush alone is only initiation. Only one request may be pending: another flush or reconfiguration reports busy. A wall deadline independent of the shared callback Handler closes an uncompleted subscription, rejecting later/queued callbacks instead of reusing their identity for a new request. Request failure also retires the subscription; no flush/configuration is retried. A completed request can be followed by a new flush or configuration. Normal sensor sample/accuracy/additional events may precede the completion and the common bounded event queue can overflow; last_flush_completed still records the last callback. Reopen explicitly after failure/revocation/restart.
Sensor additional_info events copy the public SDK type, serial, sensor ID and nullable int_values/float_values arrays (at most64 values each); floats use the existing typed db_real representation. These are provider frames such as placement/calibration/sampling data, not guest-injected commands or proof of physical accuracy. sensor_watch() registers public dynamic-sensor notifications only when Android reports support, then delivers connected/disconnected events with copied sensor metadata. It does not invent initial attach events; enumerate with sensor_list_page. Actual dynamic removal closes a matching live subscription/trigger. One-shot device_info reports kind=sensor_trigger and armed=false once the actual trigger has fired; reopening explicitly rearms a new SDK listener. Sensors consent is lazy and unchanged; activity/heart sensors still require their separate actual Android runtime permission. All resources stay workspace-owned and are closed on explicit close, Sensors revocation or process loss; no wake lock or background-delivery guarantee is added.
Direct sensor captures: sensor_direct_open(memory_type,slots) accepts "memory_file" or "hardware_buffer" and1..4096 slots of104 bytes. It attempts the real public SensorManager.createDirectChannel, even if inventory advertises no supporting sensor; SDK refusal is returned as an error, never a fabricated channel. Both backing allocation and reports require the existing lazy Sensors grant. The owned handle uses device_info/device_close; at most8 captures including pending cleanup exist globally. device_info contains memory_type, slots, bytes, record_bytes, frozen, in_flight, active reports (sensor/token/rate) and token history (sensor/type/token). A capture retains at most64 token mappings and64 active reports; open a new capture when its mapping bound is reached.
sensor_direct_configure(handle,sensor_id,rate) accepts0=STOP,1=NORMAL,2=FAST,3=VERY_FAST and returns the public SDK result (positive report token for start/change;1 for stop). Nonzero rate requires actual advertised backing/rate support and the sensor's activity/health permission. Rates are hints, not measured cadence. sensor_direct_stop(handle) asks Android to stop all reports and returns1 on SDK success. Token mappings remain available after stop/freeze so old records can still be identified; record order is physical ring-slot order. Refused SDK configuration or an SDK runtime failure retires the handle; validation errors leave it usable. The normal Android HIGH_SAMPLING_RATE_SENSORS manifest permission permits requested higher direct rates on Android12+ without another runtime dialog, but does not grant Sensors access. Android privacy toggles/background limits may still constrain delivery; no wake lock, power or background delivery guarantee is added.
sensor_direct_freeze(handle) closes the actual SDK channel while retaining owned backing memory and token mappings, returning1 when close returns. It is idempotent; frozen captures can be read but cannot restart/configure/stop reports. Open a new capture to resume. sensor_direct_read(handle,offset,count) copies1..315 whole records at a zero-based slot offset, within the allocated slots. It returns a map with offset,count,slots,record_bytes=104,frozen and data (binary blob, at most32760 bytes). Live reads are raw copies and may overlap a producer overwrite: parsing and a repeated counter alone do not prove a coherent atomic snapshot. Freeze before reading a finite capture that requires the producer to have closed; this does not add a stronger hardware memory-ordering contract than Android's public close/read API. A read/SDK failure retires the handle. Only one SDK/copy operation uses a channel at a time; concurrent operations report busy. Cancellation marks it closed promptly and defers cleanup until the current SDK operation returns. Cleanup closes the SDK channel before its backing; failed or blocked cleanup retains its global lease and is retried on a later open instead of freeing memory under a writer or admitting unbounded replacements. No failed write/configuration is replayed. Logical grant/workspace revocation closes captures, process loss discards handles, and accesses recheck the activity/health permissions for retained token mappings, including frozen captures.
Portable direct ABI helpers require no hardware grant. sensor_direct_records(blob) parses0..315 complete104-byte little-endian records into a list preserving every physical slot: a zero-counter slot becomes db_null; a nonzero row is [db_int(token),db_int(type),db_int(unsigned_counter),db_int(timestamp_ns),db_blob(payload64)]. It validates size104, positive signed token/type, nonnegative timestamp and zero reserved fields. Invalid/torn records return0 with device_error/db_error details; a valid-looking live record still does not prove coherence. Payloads stay opaque because the public union is sensor-type dependent, including vendor types. sensor_direct_f32(payload64,index0..15) returns a db_real with the exact binary32-to-binary64 numeric expansion (signed zero, subnormal, infinity and NaN payload bits retained); sensor_direct_i64(payload64,index0..7) returns the signed64-bit union element. sensor_direct_counter_distance(newer,older) returns forward distance modulo4294967295 (zero is skipped), or-1 with error details for invalid counters. It cannot infer full wrap cycles, sort physical slots, or detect all torn writes. All helpers are preloaded; do not import files in generated programs.
USB inventory returns devices/next/total, limit 1..32. Configuration/interface pages use limit 1..8. Configuration/interface/endpoint IDs come from inventory. usb_open requires separate Android device approval. Claim an interface before endpoint transfers. Control and endpoint transfers use 1..8000 ms timeouts and at most 32768 bytes. IN requires request/endpoint direction bit 128; OUT requires it clear. Reads return blobs, writes return actual byte counts.
USB serial: choose a port from serial_ports(id), then serial_open(id,port,force 0/1). serial_configure uses baud 50..3000000, data bits 5..8, parity 0 none/1 odd/2 even/3 mark/4 space, stop 0 one/1 one-and-a-half/2 two (one-and-a-half requires 5 data bits). Open defaults to 9600 8N1, DTR/RTS on and no flow control. Drivers cdc/ftdi/cp210x/ch34x run in Flexscript. serial_read/write use typed state, not a device handle; reads buffer packet remainders and writes may be partial. Use serial_close. Reopen after process restart/revocation/disconnect; saving state cannot preserve OS ownership.
Keystore: key_generate uses kind ec_p256/rsa2048/hmac_sha256/aes256 and backing any/hardware/strongbox. Aliases are workspace-scoped, 1..64 letters/digits/dot/underscore/hyphen; existing aliases cannot be overwritten. key_info reports actual Android security_level. key_sign/verify use SHA-256 and accept db_text/db_blob; verification signatures max 1024 bytes. key_public exports X.509 SPKI only; secret/private bytes cannot be exported. AES-only key_encrypt returns nonce/ciphertext blobs; key_decrypt requires the same authenticated additional data. Plaintext+aad max 32752 bytes, 12-byte nonce, 16-byte GCM tag. A new nonce is generated by Android for each encryption. Malformed signatures return false; authentication failures return an error. Keys persist across VM programs/restarts until key_delete. These keys do not require biometrics.
Audio: audio_devices returns devices/next/total, page limit 1..16. Device IDs come from inventory, or use default. Open PCM streams with rate 8000..192000 and channels 1 or 2; Android may reject unsupported formats. Encoding is signed PCM16 little-endian. Input needs microphone permission and a visible Collie activity; hiding Collie closes capture. device_read returns complete PCM frames, device_write accepts complete frames and may return a partial byte count. audio_control supports start/pause and playback-only flush while paused; audio_volume is per-stream 0..1000. audio_route selects a preferred device; device_info reports actual routed device, format and timestamps. Android may choose a different route.
MIDI: midi_list and midi_ports return devices or ports plus next/total, page limit 1..32. midi_open returns a device; midi_port_open(device,direction,number) uses send for a device input or receive for a device output. Read receive-port message/flush events with device_wait; message fields are data blob and timestamp_ns. midi_send and device_write return bytes sent; timestamp 0 is immediate, future timestamps are System.nanoTime-based and at most 60 seconds ahead. midi_flush sends a flush. MIDI byte and UMP devices are distinguished by transport/protocol; UMP sends must contain complete 32-bit words. Close ports/devices with device_close; closing a device closes its ports. MIDI watch handles report add/remove/status events. midi_bluetooth_open opens a known uppercase Bluetooth MAC through Android BLE-MIDI, asking for Nearby devices permission first; it does not scan or enable the radio.
DNS-SD: nsd_browse(type,network) and nsd_register(name,type,port,attributes,network) return resources. Use service types like _http._tcp.; selected-network support requires API33+. TXT advertising attributes are [key,text] pairs, each record max255 bytes and total1300; encode arbitrary binary as base64 text. Resolve/update attributes arrive as [key,blob] pairs. Use device_wait for started/found/lost/registered/updated/error events. Found events have id and service; service IDs belong to that browser only. nsd_services pages services/next/total (1..32); nsd_resolve returns name/type/port/network/addresses/attributes. nsd_watch_service returns an update resource on API34+. Close browser/registration/watch handles when finished. Use a LAN network, not a cellular-only connection.
VPN: vpn_open(name,addresses,routes,dns,mtu,apps,network) provides RAW IP packet transport, not encryption or peer discovery. It requires separate Collie VPN permission and Android system approval, starts while Collie is visible, and runs with a foreground service/Disconnect notification. Addresses/routes are lists of [numeric IPv4-or-IPv6,prefix_length]; routes must have zero host bits. DNS is a list of numeric addresses. MTU 576..32768 (IPv6 min1280). Apps [] means Collie only, [*] means all apps, [!package,...] excludes those packages; otherwise list allowed package names. Underlying network must be non-VPN. Only one Collie tunnel can be active. device_read must supply a limit at least MTU; device_write injects one complete packet. vpn_protect(tun,socket) excludes an owned TCP/UDP/listener transport socket from VPN routing. For TCP, net_tcp_open(network), protect, then net_tcp_dial(handle,host,port,timeout) before reads/writes. vpn_underlying changes the physical network; vpn_status reports prepared/active/owned/starting. The model's default connection uses a physical network outside Collie's own tunnel. Closing the handle/owner conversation or revoking Android VPN stops the interface; handles do not survive process restart.

Wi-Fi: wifi_info returns radio/state/support flags without connection identity; wifi_watch returns ready/state/scan_availability events. wifi_connection reads the primary Wi-Fi connection (Android-quoted SSID), not the model route. Scan/connection/request/hotspot require BOTH wifi and location grants; Android asks for precise Location, and Nearby Wi-Fi on API33+ request/hotspot calls. wifi_scan(refresh0 cached/1 request) returns a snapshot; requested scans emit scan or error and Android can throttle them. wifi_scan_page(snapshot,offset,limit1..16) returns access_points/next/total/reported_total/truncated, at most128 APs. It returns a lease, not an immediate connection. device_wait gives available/link_changed/lost/unavailable and a network selector for existing net_* calls; this never rebinds the process or model. Empty passwords only for open/owe; personal passphrases8..63 printable ASCII. wifi_suggest(ssid,security,password,hidden,metered,autojoin) returns a scoped lease, adds one Android suggestion and emits accepted/approval status (approval API31+). Close every lease/snapshot. Wi-Fi Direct uses the p2p_* functions below. Aware and RTT use the functions described below; capability rows distinguish implementation from actual device support.

Audio recording uses the first recommended audio profile; camera_video_audio_profile_options(quality,video_index,audio_index,duration_ms,max_bytes,dynamic_range,stream_use_case,color_space) selects another exact audio profile and requires the audio-start operation. Microphone consent remains separate. The SDK profile and recommended container are passed to MediaRecorder without replacing their dimensions/rate/bitrate/codec; the existing recorder bounds still apply. No preset or size is silently substituted. Time-lapse/high-speed presets require the explicit rate/session wrappers described below; using those preset classes as ordinary recording still fails before allocation.
The camera output dynamic range must match the chosen SDK encoder HDR format: SDR STANDARD1 (or default0), HLG2, HDR10=4, HDR10+=8, or an advertised Dolby Vision profile with matching8/10-bit depth. Stream use case0 and color space-1 leave SDK defaults. Non-default values require the corresponding camera SDK support and advertised PRIVATE-surface combination. device_info reports requested encoder/audio profiles and actual OutputConfiguration getters separately; MediaRecorder may alter encoding characteristics internally, so inspect the finalized container to establish effective codec/profile/color metadata. SDK configuration acceptance does not prove HDR fidelity or physical accuracy. The7-field legacy camera_video_options record remains supported unchanged.

Camera recording rates: camera_video_timelapse_options(base_options,capture_fps) wraps legacy7-field or recommended8/9-field options. Pass capture_fps as db_int or finite db_real bits,0.001..120 and below the base playback FPS. The adapter combines the public MediaRecorder capture-rate setter with individually paced SDK capture requests; the SURFACE recorder does not drop surplus frames for you. No repeating stream or missed-tick catch-up burst is used. Manual camera_capture is blocked while this recorder owns time-lapse pacing. Time-lapse records video only; audio-start is rejected rather than silently ignoring its audio. Capture rate is requested SDK sampling, not a measured physical sensor rate. Recommended time-lapse quality1000..1013 requires this wrapper.
Constrained high speed: camera_high_speed_sizes(id,offset,limit1..16) and camera_high_speed_ranges(id,width,height,offset,limit1..16) retain actual SDK sizes/ranges and a separate capability flag. No capability is inferred from normal FPS or encoder profiles. camera_video_high_speed_options(base_options,capture_fps,playback_fps,playback_bitrate) requires an advertised fixed capture range at the exact encoder size, integer120..960 capture FPS,1..capture FPS playback and64000..50000000 playback bitrate. It explicitly overrides base encoder playback FPS/bitrate. Recommended high-speed quality2000..2008 requires this wrapper. Capture>playback enables slow motion via the SDK capture-rate setter and forbids audio; equal rates leave capture-rate conversion off and can use the audio-start operation.
High-speed recording creates an actual SESSION_HIGH_SPEED (Android9+) or public constrained high-speed session (Android8), verifies the callback session type, sets the exact CONTROL_AE_TARGET_FPS_RANGE, and submits only SDK-created request lists through repeating/capture burst APIs. No ordinary-session fallback is made. An explicit conflicting FPS setting is rejected. TEMPLATE_RECORD is required while the constrained recorder is active. SDK high-speed mode overrides automatic-control/post-processing modes; other request settings remain subject to its public restrictions and actual result metadata. The owned session has one encoder output; raw/YUV/JPEG reader targets are not added. Session output range/use-case/color restrictions and SDK rejection remain explicit.
Both rate modes retain the existing Camera/Microphone, visible-Activity, file-byte, workspace and cleanup rules. For these modes duration_ms also limits wall time from actual SDK start return, including paused time, independently of encoded presentation duration. device_info gives rate_mode, capture_rate_requested as exact real bits, constrained_capture_fps, session_type, actual_high_speed_session and wall_deadline_elapsed_ms separately from actual finalized container timestamps. Wall expiry requests asynchronous stop, with getter/wait checks even if callback delivery is delayed; resource leases remain owned until actual SDK cleanup. Regular recording keeps its existing duration behavior. Actual sensor cadence, slow-motion ratio, output fidelity and physical/OEM behavior require device verification; absence of advertised high-speed capability is not a successful high-speed capture.

Explicit encoder profile/level: camera_video_encoding_options(base_options,profile,level) is an outer wrapper around regular, time-lapse or constrained-high-speed options, including recommended profiles. Both values are positive public MediaCodecInfo.CodecProfileLevel integers. Legacy DEFAULT codec is rejected because its profile namespace is unspecified; choose codec1AVC/2HEVC/3AV1. The public MediaRecorder.setVideoEncodingProfileLevel request is applied after base/recommended encoder settings and before prepare. device_info.encoding_profile_level_requested preserves the exact request separately from the recommended profile. Android may ignore/alter it; only the actual encoded track establishes effective profile/level. This wrapper is outermost; rate/encoding wrappers cannot be repeated or nested in the opposite order.
Encoder SDK inventory uses the same legacy codec selector1AVC/2HEVC/3AV1. camera_video_codecs(codec,offset,limit1..16) pages the actual REGULAR_CODECS encoders in SDK order, retaining exact name/MIME, profile-level count and SURFACE input support. Android10+ canonical name/alias/hardware/software/vendor flags are actual SDK getters; older versions return typed null. camera_video_codec_profiles(codec,name,offset,limit1..16) pages actual profile/level pairs in SDK order. These can describe a maximum level rather than every usable lower level; an absent exact pair is not automatically an invalid request. camera_video_codec_info(codec,name) returns actual width/height/FPS/bitrate ranges, alignments, encoder quality/complexity and CQ/VBR/CBR support. camera_video_codec_support(codec,name,width,height,fps,bitrate) asks that exact codec's public isFormatSupported for the full SURFACE format; independent width/height/FPS ranges do not prove the combination. These snapshots require Collie Camera permission, without Android capture or Microphone permission. Names must belong to the actual encoder/MIME inventory; no arbitrary codec instantiation occurs. MediaRecorder does not let this API select a particular codec implementation, so inventory/format support does not promise which encoder it will use or successful recording/HDR/physical fidelity.

Haptics: haptic_info reports actual actuator/amplitude support, SDK API provenance, foreground requirement and whether the single app-wide actuator lease is busy. haptic_play(duration_ms1..2000,amplitude-1default/1..255) and haptic_waveform(timing_list,amplitude_list) return owned device handles. Waveforms have1..64 matching integer rows, timing0..2000ms, amplitude0silent/-1default/1..255 and total1..2000ms, without repetition. Close with device_close; a second playback is busy until the current SDK cancellation returns, including locally closed resources waiting for cleanup. This prevents an old handle from stopping another conversation's vibration on Android's shared app vibrator token. Expiry stops and releases the SDK lease but retains readable handle metadata until close; stale close cannot cancel a later owner.
Haptic playback requires a visible Activity and the existing Haptics grant. Android's VIBRATE permission is declared normally, with no runtime dialog. Actual onStop, workspace closure, revocation, cancellation and a bounded wall deadline request asynchronous SDK cancel off the UI thread. Each deadline starts when SDK vibrate returns. A dedicated in-process scheduler requests cancellation independently of the shared hardware event Handler or further VM access; the separate bounded cleanup worker performs SDK cancel. Cleanup retries use the same independent scheduler, retaining the app lease until actual cancel returns. Cancelled deadline/retry tasks are removed immediately; the single app-wide owner bounds retained tasks. device_info/device_wait remain fallback guards if deadline scheduling is delayed. Scheduling is not hard real-time, and SDK/Binder/OS suspension or process death can affect timing; no physical latency guarantee is made. The lease remains held through SDK startup and actual cancel return; failed/queued cleanup retains ownership and retries only idempotent cancel, never playback. device_info separates requested, sdk_vibrate_called/returned, sdk_cancel_returned, lease_released, wall_deadline_elapsed_ms, stop_requested_elapsed_ms, stop_reason and error. submitted means the SDK call returned, not that Android played it or a physical actuator moved. SDK/OS policy or another application can suppress/preempt vibration.
Predefined effects: haptic_effects() lists public IDs0CLICK,1DOUBLE_CLICK,2TICK,5HEAVY_CLICK. play_api requires Android10; native_support is the actual SDK0UNKNOWN/1YES/2NO on Android11+, otherwise typed null. These support codes describe optimized hardware implementation; Android may use its own fallback for NO/UNKNOWN. haptic_effect(id,duration_limit_ms1..2000) submits the public predefined effect unchanged on Android10+, with the explicit wall limit. No fallback waveform is fabricated by Collie.
Primitive composition: haptic_primitives() lists public IDs1CLICK,2THUD,3SPIN,4QUICK_RISE,5SLOW_RISE,6QUICK_FALL,7TICK,8LOW_TICK. supported is the actual SDK boolean on Android11+, otherwise null; individual_support_known becomes true on Android12 because Android11 only reports aggregate composition capability. duration_ms is the actual SDK estimate on Android12+ (0 for unsupported), otherwise null. haptic_primitive(id,typed_scale,delay_ms) builds[id,scale,delay]; scale uses db_int or finite db_real bits in0..1, delay0..2000ms. haptic_compose(steps,duration_limit_ms1..2000) accepts1..32 such rows, with total delays<=2000ms, submits a public SDK composition on Android11+ and rejects actual SDK-unsupported primitives without substitution. The wall limit may clip a long sequence; requested composition and duration estimates are not proof of full playback or physical force/timing. Explicit actuator selection and common-limit parallel graphs are available through the actuator API below.


Envelopes/frequency: haptic_envelope_info() uses the existing Haptics grant. resonance_api is Android14+; resonant_frequency_hz/q_factor are actual SDK values (null for unavailable/NaN). envelope_api is Android16+; envelopes_supported, envelope_limits and frequency_profile are actual SDK facts or typed null when unavailable. SDK maximum_size, minimum/maximum_point_duration_ms and maximum_duration_ms are distinct from Collie's32-point/2000ms request bounds. The default Vibrator may represent a composite actuator; explicit per-ID metadata and selection use the actuator API below.
haptic_frequency_profile(offset>=0,limit1..16) pages the actual Android16 frequency-to-maximum-acceleration map in SDK order. points contain integer frequency_hz and exact typed real maximum_acceleration_g; count/offset/next/complete describe the actual page. Exact EOF or a larger offset returns empty points. haptic_frequency_response(typed_frequency_hz) delegates SDK interpolation, including the SDK's out-of-range response. haptic_frequency_range(typed_minimum_acceleration_g) delegates the SDK's achievable frequency range; range is null when impossible. Requested values are retained separately from sdk_frequency_hz/sdk_minimum_acceleration_g because the SDK accepts float. Inputs use finite nonnegative db_int/db_real values (frequency strictly positive), rejecting float overflow/underflow. Older Android returns unsupported_operation; an absent actual frequency profile returns unsupported_combination. No frequency curve or distance/force measurement is fabricated.
haptic_envelope_point(typed_strength,typed_sharpness_or_frequency,duration_ms) builds a portable three-item record. haptic_envelope_basic(typed_initial_sharpness,points,duration_limit_ms1..2000) uses Android16 BasicEnvelopeBuilder: intensity/sharpness in0..1, implicit initial zero intensity, final intensity exactly zero. haptic_envelope_waveform(typed_initial_frequency_hz,points,duration_limit_ms1..2000) uses WaveformEnvelopeBuilder: amplitude0..1 and positive Hz within the actual SDK frequency range, with implicit initial zero amplitude. Unlike basic envelopes, a waveform need not end at zero. Both accept1..32 points, positive integer segment durations within actual SDK bounds and total<=2000ms/SDK maximum duration. The framework may split a graph exceeding its native point capacity. These operations require actual envelope support and use the existing visible-Activity, exclusive lease, async cancellation, ownership/revocation and wall-deadline rules; duration_limit_ms is explicit and may clip the requested graph. device_info.requested retains exact typed points/initial/requested_duration_ms, separately from the submitted SDK float effect and wall limit. No fallback effect is substituted for unsupported envelopes or waveform frequencies; SDK submission is not a physical-playback receipt.


Actuator selection/parallel graphs (Android12+): haptic_actuators(offset>=0,limit1..16) pages the actual SDK VibratorManager IDs in SDK order, with present/amplitude_control, count/offset/next/complete and maximum_targets=8. Empty or EOF pages remain empty; older Android returns unsupported_operation rather than inventing IDs. haptic_actuator_info(id) returns that exact SDK vibrator's haptics/effects/primitives/envelope metadata. haptic_actuator_frequency_profile(id,offset,limit), haptic_actuator_frequency_response(id,typed_hz), and haptic_actuator_frequency_range(id,typed_minimum_acceleration_g) use the selected vibrator's Android16 profile/getters; their older-version/absent-profile errors remain unchanged. IDs must still belong to the actual SDK inventory; no arbitrary device path or Java dispatch is accepted.
Pure record factories (no playback): haptic_once(duration_ms1..2000,amplitude-1default/1..255), haptic_pattern(timings,amplitudes), haptic_predefined(id), haptic_composition(primitive_steps), haptic_basic(typed_initial_sharpness,points), and haptic_frequency(typed_initial_hz,points). Their tags are one_shot, waveform, predefined, composition, basic_envelope and waveform_envelope, with exact typed arguments. Android validates these using the same SDK builders/bounds/support checks as the existing direct playback functions. Constructing a record alone does not validate a device, acquire a resource or emit a haptic effect.
haptic_target(id,effect_record) builds[id,effect]. haptic_on(id,effect_record,duration_limit_ms1..2000) submits one target. haptic_render(target_list,duration_limit_ms1..2000) submits1..8 distinct actual SDK actuator IDs as one public CombinedVibration parallel graph. Every target/record passes bounded validation and available public SDK support checks before submission; unknown/duplicate IDs, detected unsupported combinations or malformed later entries reject the whole graph before partial submission. SDK return is not acknowledgement that Android accepted/played the complete graph: it can still ignore a combination despite reporting primitive support (for example, a primitive delay exceeding an internal controller limit not exposed by this public API). The explicit wall limit is common to all targets, with no independent per-target clipping or guarantee of simultaneous physical onset. Effects may naturally finish earlier while metadata/lease remains until close or the common limit. device_info.requested contains type=parallel, exact original targets, target_count and common_duration_limit_ms. Submission returns the usual workspace-owned haptic handle.
All direct, selected and parallel playback shares one app-wide lease. Selecting distinct IDs does not create independent cancellation tokens: Android manager cancellation can affect the entire app graph. Foreground, revocation, cancel, asynchronous cleanup and independent deadline/retry rules still apply; the lease is held until actual SDK cancel returns. No default-motor substitution is performed for an unknown/unsupported requested target. Actuator IDs and SDK graph submission are not proof of two physical motors, physical placement, synchronized onset, measured force/frequency or physical accuracy.

Primitive timing: haptic_primitive_delay(id,typed_scale,delay_ms,delay_type) returns the four-field inert record[id,scale,delay_ms,delay_type]. Type0 is a pause after the preceding primitive ends, exactly the existing haptic_primitive default. Type1 is an offset relative to the preceding primitive's start; haptic_primitive_offset(id,typed_scale,offset_ms) constructs type1. Android16+ uses the public four-argument builder; older Android accepts explicit type0 through its equivalent default-pause API but rejects type1 with unsupported_operation, never converting an offset into a pause. Android may drop an overlapping relative primitive. haptic_primitives.relative_start_offset_api reports SDK API availability, not device timing/physical verification. Both direct haptic_compose and selected/parallel haptic_composition records share the same validation and public builders:1..32 primitives, IDs1..8, finite typed scales0..1, delays0..2000, delay types0/1, and sum of requested delays <=2000ms. The separate common wall limit1..2000ms still cancels SDK playback and bounds ownership, independent of primitive duration, skipped segments or physical timing. requested steps preserve exact three-/four-field records and typed scale bits; no partial playback or lease is started for a malformed later record.

Bounded record playback: haptic_submit(effect_record,duration_limit_ms1..2000) submits a default-actuator effect record under an explicit common wall deadline, including finite records; a finite source can finish sooner. requested has type=effect, the exact supplied effect record and common_duration_limit_ms. It uses the same factory as haptic_on/haptic_render, existing Haptics permission, foreground check and app-wide lease. All record validation completes before lease/playback. API availability is separate from physical support: haptic_info (and per-ID haptics metadata) reports waveform_loop_api=true and repeating_effect_api=(Android16+).
Repeating records are inert: haptic_loop(timings,amplitudes,repeat_index) returns[waveform_loop,timings,amplitudes,repeat_index], preserving a once-only prefix and repeating the suffix at index0..length-1 via the public waveform repeat API (Android8+). Use1..64 matching arrays, integer durations0..2000, amplitudes-1default/0..255, positive total duration<=2000ms and a positive-duration repeating suffix; an all-zero suffix is rejected. haptic_repeating(effect) returns[repeating,effect]; haptic_repeating_after(preamble,effect) returns[repeating_after,preamble,effect]. Both arbitrary-effect constructors require Android16+ and finite inputs (any existing finite record type); nested arbitrary repeats or waveform loops as inputs are invalid_argument. The latter plays its finite preamble once, then repeats the finite second effect. Older SDKs return unsupported_operation for valid arbitrary-repeat requests without converting them to waveform/finite substitutes. Each finite source retains its normal validation/bounds; constructing a record alone validates no SDK and starts no playback. Direct/default and selected/parallel paths share these rules.
The underlying SDK repeat is infinite; Collie still requires an independent1..2000ms common wall deadline and retains its exclusive playback lease until actual SDK cancel returns. Explicit close, grant revocation, Activity onStop, workspace/program cancellation and process rules still apply. A finite pattern's duration is not the common wall limit, and neither graph submission nor the deadline proves physical onset/accuracy. Zero-duration source segments are retained for Android's normal handling; no source/index/scale is clamped or silently substituted.

Document stream reliability: device_info on document_file/document_typed_file reports reliable_errors from the actual SDK descriptor. When supported, a provider-reported reliable-pipe error/crash is checked at EOF and is returned as disconnected, with that stream closed and its descriptor released; it is not a clean db_null EOF. Typed-stream I/O errors and terminal poll/descriptor errors likewise retire the stream. Exact partial bytes already read remain partial data; a later failure is not promoted to successful completion. Normal EOF/asset boundaries remain db_null; ordinary read timeouts preserve the stream for a later explicit read. A descriptor without a reliable channel cannot positively distinguish every remote error from EOF. Document queries, conversion metadata and open streams use public unstable provider clients, avoiding Android's stable-provider dependency kill mechanism. Each stream owns its client until close/failure; failed construction releases the client too. Provider Binder death during a tree operation closes that tree and its streams. A stream's reliable peer failure closes that stream; other streams discover their own failures when used. Explicitly reopen/re-enumerate after provider failure; uncertain mutations are never automatically replayed, and a provider might have changed storage before a failure was observed.
